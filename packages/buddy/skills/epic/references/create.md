# Create

Plan new work as an epic, judge the plan, and file the epic and its children.

1. **Outcome first.** Ask for the outcome (one sentence: what is true when this is done) and how anyone will know it is done. Ask for the category (bug, feature, task) when it is not clear. Do not name a child before the outcome and done-when are settled.
2. **Level check.** Read the epic level's `Too big` and `Too small` in `project-tracker.levels`. Too big: suggest an initiative (the `initiative` skill when it is installed). Too small: suggest an issue (the `issue` skill). Only suggest. Continue at this level when the user does not change it.
3. **Settle the plan** as the skill's Plan section says, section by section, judging each against `project-tracker.criteria.epic`. Within that:
   - **Open questions.** List what is decided and what is not known yet. An unknown that has a findable answer becomes a **spike**: a child task titled `Spike: <question>`, done when a written answer exists, and ordered before the children that depend on it. An undecided design (what to build, or how it should behave) becomes a separate design issue, linked from `Open questions`, and the work that depends on it waits for it. Neither one is guessed into a child (EP6).
   - **Children.** Propose child issues, each independently shippable with one owner, and give each a title, a category, an executor, and a one-line done-when. Run each through the issue level's `Too big` check. A child that meets it is split, or named as a spike. Ask for the owner's priority. Then try one setup other than the default against the breakdown, such as another tracker for some category, or a team that overrides a step. Add a child when that setup needs one.
   - **Dependencies.** For each child, name the output of another child it uses. That child is its blocker, and nothing else is (EP9). Derive the run order from them.
   - **Executors and irreversible steps.** Mark each step `project-tracker.executors` says an agent cannot do as a person's step, by handle. List each irreversible step under `Risks and irreversible steps`, with the confirmation it waits for (EP7, EP8).
4. **Trackers.** Resolve the epic's tracker, and each child's. A child on another tracker than the epic cannot be a native child. It is linked in its body and listed in the epic's body by title, or as tracked internally when the epic is public and the child's tracker private.
5. **Search for duplicates.** Run the epic tracker's `Search` at least twice for the epic (the full title, then the core noun and verb), and once for each child on that child's tracker. Show each hit (title, state, URL, level).
   - A hit the user says is the epic, when it is an epic with no children (a **shell**, as `initiative` files them): break it down. It is the epic, step 7 creates nothing and leaves its body, and step 1 starts from its `Outcome`.
   - A hit the user says is the epic, otherwise: stop, and offer Promote (an issue), Demote (an initiative), or Revise (an epic) on it.
   - A hit the user says is a child: attach it instead of creating it.
6. **Show the plan, and confirm unless the user owns every tracker.** Run each tracker's `Kinds`, and the level-label check its `Retype` Limits give, when it gives one. Show the epic (title, category, outcome, key terms, non-goals, open questions, done-when, tracker, and the level label or field it uses), each child in run order (title, category, spike or not, executor, blockers, tracker, created or attached), each irreversible step, the final pass or fail of each planning criterion, and, on its own line, any level label that is missing and will be created. Then run `Ownership` on every tracker the plan writes to (its format is in `project-tracker.capabilities.interface`).
   - **Every one answers `owned`**, the level check in step 2 found nothing, `Open questions` holds nothing the user must decide, and no level label is missing: show the plan and go to step 7 in the same turn. Do not wait for a reply.
   - **Otherwise** (a tracker answers `not owned` or its ownership is unknown, the level check found the epic too big or too small, an open question needs the user, or a level label is missing): ask once for the whole plan. Do not create anything without it. A missing label is created, with the reference's command, only on a yes to that line.
7. **Create the epic.** Run its tracker's `Create` at level epic, with the body written to a file from `project-tracker.template.epic`. Under `Child Issues`, list the planned children by title, as the Guards allow. The tracker's native link carries their numbers.
8. **Create the children.** Create each child, in run order, through the `issue` skill when it is installed. Pass the title, category, body, tracker, and the epic as parent, and say the search and the confirmation are done. Otherwise run the child tracker's `Create` with its template reference (`project-tracker.template.<category>`) and the epic as parent. Each child's body names its executor and the outputs of its blockers it uses. Attach each existing match with the `Link` section. After a failed create, follow the Guards before the next child.
9. **Link the plan.** Under the same confirmation: add the blockers with the tracker's `Depend` section; add the epic and each child to the board with `Board`, when the routing or the user names one; post the research artifact as `research.method` says and link it; then rewrite the epic's body with the children's numbers in `Run order`, and run `Sync body`.
10. **Read back.** Run [Validate](../SKILL.md#validate) V1 to V5. Report each check that fails, with what fixes it.
11. **Report.** The epic's URL, then each child's URL in run order, marking spikes, design issues, and attached items, and anything not filed, with why.
